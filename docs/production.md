# Продакшен: Compose за SafeLine WAF

Локальная разработка идёт без WAF (`npm run up`). На сервер ставят тот же стек с оверлеем `infra/docker-compose.prod.yml` и отдельным проектом SafeLine.

## Что открыто наружу

```text
интернет ── 80/443 ──> SafeLine tengine (network_mode: host)
                          ├── app.example.com   ──> 10.88.0.1:3000  Next.js
                          ├── api.example.com   ──> 10.88.0.1:8000  Kong (Auth, REST, Realtime, Storage, Functions)
                          └── sonar.example.com ──> 10.88.0.1:9000  SonarQube
```

`10.88.0.1` — это `UPSTREAM_ADDR`, адрес на dummy-интерфейсе `upstream0`. Снаружи он не маршрутизируется. SafeLine 9.4.3 и новее не принимает `127.0.0.1` как upstream сайта: такой сайт отвечает 502. Публиковать эти порты на `0.0.0.0` тоже нельзя: Docker обходит ufw.

| Порт на хосте | Кто слушает | Доступ |
| --- | --- | --- |
| 80, 443 | SafeLine | Интернет |
| 22 | sshd | Интернет, только по ключу |
| 10.88.0.1:3000 | Next.js | Только SafeLine на этом хосте |
| 10.88.0.1:8000 | Kong | Только SafeLine на этом хосте |
| 10.88.0.1:9000 | SonarQube | Только SafeLine на этом хосте |
| 127.0.0.1:9443 | Консоль SafeLine | SSH-туннель |
| 127.0.0.1:54323 | Studio, только с `--profile admin` | SSH-туннель |

Postgres 5432 в проде на хост не публикуется. Он доступен только контейнерам внутри сети Compose. База SonarQube тоже остаётся внутри сети: наружу смотрит только веб-интерфейс.

Docker публикует порты в обход ufw и firewalld. Поэтому защищает не фаервол, а адрес публикации: `127.0.0.1` или частный адрес, не `0.0.0.0`. CI-джоба `compose` падает, если порт смотрит в интернет.

## Сервер

Один Linux-сервер на приложение, SafeLine и SonarQube. `network_mode: host` у tengine работает только на Linux, на macOS прод-стек не запускают.

| | Минимум, чтобы стек встал | Для этого шаблона |
| --- | --- | --- |
| CPU | 4 vCPU | 4–8 vCPU |
| RAM | 8 GB | 16 GB |
| Диск | 40 GB SSD | 80 GB SSD |

На 4 GB стек не рассчитан. На 8 GB он поднимается, но SonarQube (три кучи по 512 МБ, живой RSS обычно 2.5–3.5 GB) и SafeLine (ещё 2–4 GB) делят память с Supabase и лимитом функций в 1 GB. Во время скана CI этого мало. Образы сами по себе тяжёлые: Postgres Supabase около 1.3 GB, SonarQube около 1.5 GB, SafeLine около 2 GB. 40 GB диска хватает на первый запуск, 80 GB оставляют место на тома, логи и обновления.

Три DNS-имени типа A на публичный IP сервера: `app.example.com`, `api.example.com`, `sonar.example.com`. Записи нужны до выпуска сертификата.

Фаервол второй рубеж, не единственный. Опубликованный Docker-порт его обходит, поэтому сервисы приложения не вешают на `0.0.0.0`.

```bash
ufw default deny incoming
ufw allow 22/tcp
ufw allow 80/tcp
ufw allow 443/tcp
ufw enable
```

## Запуск

На сервере, в клоне репозитория. Сначала адрес, на котором будут слушать приложение, Kong и SonarQube. Он должен пережить перезагрузку: без него compose не сможет занять порт.

```bash
sudo sh infra/scripts/upstream-addr.sh 10.88.0.1
```

Чтобы адрес поднимался сам, положите тот же вызов в oneshot-юнит systemd и включите его. Не берите адрес из подсети SafeLine (`10.222.222.0/24` при `SUBNET_PREFIX` по умолчанию) и не берите `127.0.0.0/8`, `169.254.0.0/16`, `0.0.0.0`.

```bash
npm run keys:prod -- --app-url https://app.example.com --api-url https://api.example.com --sonar-url https://sonar.example.com
```

`npm run keys:prod` создаёт два файла с правами 0600, оба в `.gitignore`, и пишет `UPSTREAM_ADDR=10.88.0.1`:

- `infra/.env.prod` — переменные Supabase, приложения и `SONAR_PUBLIC_URL`. Публичные URL уже прописаны, автоподтверждение почты выключено.
- `infra/safeline/.env` — переменные SafeLine. Файл отдельный, потому что у SafeLine свои `POSTGRES_PASSWORD` и `REGION`, и в общем файле они затёрли бы переменные Supabase.

Ключи генерируйте на самом сервере. `ARCH_SUFFIX` выбирается по архитектуре машины, на которой запущен скрипт: на arm64 это `-arm`, на amd64 пусто.

Заполните `SMTP_*` в `infra/.env.prod`. В проде регистрация подтверждается письмом, и без SMTP стек не стартует: compose остановится с ошибкой `required variable SMTP_HOST is missing`.

```bash
npm run up:prod
npm run waf:up
npm run waf:reset-admin   # печатает логин и пароль консоли SafeLine
```

SafeLine хранит данные в `SAFELINE_DIR` (по умолчанию `/data/safeline`). Его запускают отдельным compose-проектом `safeline`, поэтому `npm run up:prod` при деплое приложения WAF не перезапускает.

## Настройка SafeLine

Консоль открывается только через туннель:

```bash
ssh -L 9443:127.0.0.1:9443 user@server
# в браузере https://localhost:9443, сертификат самоподписанный
```

1. Добавьте три приложения (сайта), все на порту 443 с HTTPS:
   - `api.example.com`, upstream `http://10.88.0.1:8000`;
   - `app.example.com`, upstream `http://10.88.0.1:3000`;
   - `sonar.example.com`, upstream `http://10.88.0.1:9000`.
   Если `UPSTREAM_ADDR` другой, подставьте его. `127.0.0.1` консоль 9.4.5 отвергнет.
2. Сертификат выпустите до переключения в режим блокировки. Как именно, в разделе ниже. Включите редирект с 80 на 443 после того, как сертификат уже получен: в 9.4.1 это чинили, но проверка HTTP-01 всё равно идёт на порт 80.
3. Режим защиты переключите с наблюдения на блокировку, когда убедитесь, что обычные сценарии (вход, создание заметки, открытие SonarQube) не режутся.
4. Включите ограничение частоты запросов. В первую очередь оно нужно для `api.example.com/auth/v1/*`, где подбирают пароли.
5. Не включайте JS-проверку ботов и аутентификацию SafeLine на `api.example.com` и на `sonar.example.com`. Клиент Supabase и сканер SonarQube ходят через обычный HTTP и такую проверку не пройдут. Картинки в комментарии pull request GitHub тоже качает с `sonar.example.com` без браузера. На `app.example.com` проверку можно включать.
6. Проверьте Realtime: он работает по WebSocket через `api.example.com/realtime/v1/`.

## Сертификат

Публичные сертификаты живут только в SafeLine. Next.js, Kong и SonarQube наружу отдают HTTP на `UPSTREAM_ADDR`. Консоль SafeLine на `127.0.0.1:9443` остаётся с самоподписанным сертификатом и через туннель. Отдельный сертификат для неё не нужен.

В Community 9.4.5 по журналу изменений SafeLine умеет три вещи:

- бесплатный сертификат Let's Encrypt по ACME HTTP-01, с автопродлением;
- загрузку своего сертификата и ключа, в том числе вставкой текста, форматы ключа PKCS#1, PKCS#8 и ECC;
- подмену уже загруженных файлов сертификата в каталоге данных SafeLine: процесс перечитывает их примерно раз в час.

Встроенный ACME не выпускает wildcard: для `*.example.com` нужен DNS-01, а в журнале SafeLine описан только HTTP-01. Три имени этого шаблона кладут в один сертификат: `app.example.com`, `api.example.com`, `sonar.example.com`. Так одно продление закрывает все сайты. Отдельный сертификат на каждое имя тоже годится, если имена уже заведены как три сайта.

Порядок в консоли (Settings → SSL Cert, в русской сборке пункт может называться иначе):

1. DNS всех трёх имён уже смотрит на этот сервер, порт 80 открыт с интернета.
2. Add certificate → Get free cert. Укажите три имени без пробелов и без `https://`. Пробел в имени ломал выпуск.
3. Привяжите сертификат к трём сайтам и включите SSL на порту 443.
4. TLS 1.0 и 1.1 не включайте. С 9.4.1 по умолчанию остаются TLS 1.2 и 1.3.
5. После этого включите редирект с 80 на 443.

Продление бесплатного сертификата SafeLine делает сам. Ключ и сертификат лежат в `SAFELINE_DIR`, в git их не кладут: `.gitignore` закрывает `.pem`, `.key`, `.crt`, `.cer`, `.csr`, `.p12` и `.pfx`.

Свой сертификат загружают тем же экраном, если Let's Encrypt недоступен. В поле сертификата нужна полная цепочка, не только листовой сертификат. Имена в сертификате должны совпадать с именами сайтов.

Почта регистрации ходит через внешний SMTP. Сертификат для неё SafeLine не выпускает. У провайдера почты отдельно заводят SPF, DKIM и DMARC для домена отправителя.

## SonarQube и GitHub

SonarQube здесь один на всех. Локально `npm run up` его не поднимает: личный инстанс не виден остальным и не принимает отчёты из GitHub Actions. CI ходит на `SONAR_HOST_URL`, это публичный адрес за SafeLine.

После первого старта сервер несколько минут поднимает индексы. Первый вход: `admin` / `admin`, пароль сразу смените.

`SONAR_PUBLIC_URL` compose кладёт в `sonar.core.serverBaseURL`. Ссылки в комментариях GitHub берутся отсюда. Поле в интерфейсе (Administration > Configuration > General settings > General > Server base URL) контейнер перебивает своим значением. Менять адрес нужно в `infra/.env.prod` и пересоздавать контейнер.

Дальше:

1. В SonarQube: My Account > Security, токен. В секреты репозитория GitHub положите `SONAR_TOKEN` и `SONAR_HOST_URL` (`https://sonar.example.com`, тот же адрес, что `SONAR_PUBLIC_URL`). Ключ проекта берут из `sonar-project.properties`. В шаблоне это `template-for-mvp`, в новом репозитории его меняют на имя репозитория, иначе анализы разных сервисов смешаются. Первый анализ создаёт проект, если у токена есть право создавать проекты.
2. Administration > Configuration > General settings > DevOps platform integrations > GitHub > Create GitHub App. Укажите организацию и поставьте приложение на репозиторий. Базовый URL к этому моменту уже публичный, иначе GitHub вернёт браузер на localhost. Кнопка есть благодаря webapp из плагина ветвей: в чистом Community её нет.
3. Сначала должен пройти анализ ветки по умолчанию (push в `main`). Плагин ветвей не оформляет pull request, пока целевая ветка ни разу не проанализирована. На pull request CI передаёт `sonar.scm.revision`, без него комментарий в GitHub не появляется.
4. Если в комментарии pull request нет картинок, GitHub не смог скачать их с сервера. Тогда в General > Pull Request > Images base URL поставьте `https://raw.githubusercontent.com/mc1arke/sonarqube-community-branch-plugin/master/src/main/resources/static`.

## Обслуживание

Studio в проде по умолчанию не запущен:

```bash
docker compose --env-file infra/.env.prod -f infra/docker-compose.yml -f infra/docker-compose.prod.yml --profile admin up -d studio
ssh -L 54323:127.0.0.1:54323 user@server   # http://localhost:54323
```

Studio не спрашивает пароль, если открыть его напрямую через туннель. Пока он запущен, он доступен ещё и через Kong на `api.example.com/` под basic auth из `DASHBOARD_USERNAME` и `DASHBOARD_PASSWORD`. После работы остановите его: `docker stop mvp-studio-1`.

Обновление приложения: `git pull && npm run up:prod`. Новые миграции применит сервис `migrate`.

## Что проверено, а что нет

Проверено:

- `docker compose config` для дев- и прод-вариантов;
- что в проде нет публикации 5432 и Studio, а приложение, Kong и SonarQube публикуются на `UPSTREAM_ADDR`, не на `0.0.0.0`;
- что без SMTP прод не стартует;
- что пароли Postgres у SafeLine и Supabase разные;
- что сервисы SafeLine поднимаются и консоль отвечает на `127.0.0.1:9443`.

Не проверено: tengine в host-сети на Linux-сервере, выпуск сертификата в консоли, отказ 9.4.5 принимать upstream `127.0.0.1` (это текст журнала изменений 9.4.3, на этой машине сайт не создавался), блокировка и rate limit на живом трафике. Названия пунктов в интерфейсе могут отличаться от журнала SafeLine 9.4.
