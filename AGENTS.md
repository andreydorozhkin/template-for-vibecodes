# Правила для агентов

Этот репозиторий — каркас сервиса. Агент, который работает в проекте из этого шаблона, следует правилам ниже. Если правило кажется неудачным, его всё равно выполняют и пишут замечание в описании pull request, а не меняют стек молча.

## Стек

Решения зафиксированы. Их не упрощают и не заменяют.

- Язык везде TypeScript.
- Фронтенд: Next.js (App Router) в каталоге `app/`. UI собирают из **Radix Themes** (`@radix-ui/themes`). Правила — `docs/ui.md`. Не добавляют Tailwind, shadcn и другие UI-библиотеки без явной просьбы человека.
- Бэкенд: self-hosted Supabase. Вся серверная логика — только Supabase Edge Functions (Deno, TypeScript) в `supabase/functions/`.
- В Postgres нет логики приложения. В `supabase/migrations/` только схема таблиц и политики Row Level Security. Запрещены функции, триггеры, `pg_cron` и любой другой исполняемый код в базе.
- Авторизация — только Supabase Auth. Свою авторизацию (сессии, пароли, JWT) не пишут.
- В рабочем коде нет SQLite и нет подмены базы моком. Мок допустим только в тесте, на границе зависимости.
- RLS включён на каждой таблице в той же миграции, которая её создаёт. Политики описывают, кто читает и кто пишет строки.
- Клиент и Edge Functions ходят в Postgres от имени пользователя: anon-ключ плюс JWT пользователя, чтобы сработали политики RLS.
- Ключ `service_role` запрещён в клиентском коде. В Edge Function он допустим только как исключение, и в описании PR есть отдельное обоснование, почему RLS и JWT пользователя недостаточны.

SQL в `infra/db/init/` — служебный bootstrap образа Supabase (роли, схемы платформы). Это не место для логики приложения и не образец для миграций.

## Новый сервис из шаблона

Когда человек просит «собери сервис на основе этого репозитория» / «заведи проект из шаблона», агент делает по порядку:

1. `git remote -v`. Если `origin` ведёт на шаблон или remote нет — спросить URL нового репозитория. Remote самому не переписывать и не создавать репозиторий на GitHub.
2. Имя репозитория взять из URL (последний сегмент, без `.git`) и записать вместо `template-for-vibecodes`:
   - `sonar.projectKey` и `sonar.projectName` в `sonar-project.properties` (нужно, если позже включат Sonar);
   - `project_id` в `supabase/config.toml`;
   - `name` в корневом `package.json`, строчными буквами.
   Пока в этих полях `template-for-vibecodes` и человек заводит новый сервис, а не правит сам каркас, пуш в новый remote запрещён.
3. `npm run keys` → `npm run up`. Проверить, что открываются login и notes на http://localhost:3000. После смены ключей: `npm run down` и удаление томов проекта `mvp`, иначе пароли ролей Postgres не совпадут.
4. Напомнить человеку, что агент не делает в GitHub: секреты деплоя (`DEPLOY_KEY`, `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_PATH`), опционально `SONAR_*`, защита ветки `main`, первый ручной подъём сервера (`docs/production.md`). Не сообщать, что секреты уже стоят.
5. Дальше обычный цикл: story в `docs/stories/` → ветка → тесты → реализация → PR.

Пушат только по явной просьбе человека. В remote шаблона свои изменения не отправляют.

## Встроенный трекер (docs/stories)

Бэклог задач живёт в репозитории. Внешний трекер (MCP) и GitHub Projects не обязательны: без них цикл полный, шаги снаружи просто пропускают — без ошибок и без требования токенов/`gh`.

- Один файл = одна задача: `docs/stories/<id>-<slug>.md` (frontmatter + тело по `docs/user-story-template.md`).
- Статусы: `backlog` | `in_progress` | `done`. Опционально `branch`, `pr`, `external`.
- Read-only борд: открыть `docs/stories/board.html` в браузере (без `npm run`). После создания или смены статуса обновить снимок: `npm run stories:board`.
- Идея в чате без файла → сначала создать story (`backlog` или сразу `in_progress`).
- «Положи в бэклог» → только файл, без ветки и кода.
- «Сделай / возьми» → `in_progress`, ветка `feat/<id>-short-name`, дальше тесты и реализация.
- Готово → `status: done`, заполнить `branch` / `pr` при наличии.
- Если человек дал задачу из внешнего MCP-трекера — зеркалить формулировку в `docs/stories/` и указать `external`. Нет трекера — этот шаг не делают.
- Человек может сам положить `.md` в `docs/stories/`; агент уважает файл как источник правды.

Подробности: `docs/stories/README.md`, дизайн — `docs/superpowers/specs/2026-11-23-in-repo-story-tracker-design.md`.

## Порядок работы

1. Оформить user story в `docs/stories/<id>-<slug>.md` по `docs/user-story-template.md` (или взять уже лежащую в бэклоге). Обновить `board-data.js`.
2. Написать тесты из критериев приёмки и убедиться, что они падают.
3. Написать реализацию, пока тесты не станут зелёными.
4. Одна задача — одна ветка — один pull request. Ветку не переиспользуют для следующей задачи. В PR — ссылка на файл story.
5. Мерж только при зелёном CI. Красный пайплайн не обходят и не отключают. В `main` агент не пушит. После готовности — `status: done` и снова `npm run stories:board`.

## Перед пушем

1. Посмотреть `git remote -v` и состав коммита (см. «Новый сервис из шаблона»).
2. В индексе не должно быть `.env`, `infra/.env`, `infra/.env.prod`, `infra/safeline/.env`, `app/.env.local`, дампов и токенов. `npm run keys` пишет только локальные файлы, их не добавляют и не читают.
3. Прогнать команды ниже. Пока хоть одна красная, не пушат:
   - `npm run lint`
   - `npm run typecheck`
   - `npm test`
   - `npm run test:functions`
   - gitleaks по истории git. Сканер каталога не запускают: рядом лежат локальные `.env`, и в отчёт попадут секреты, которых в git нет.

```bash
docker run --rm -v "$PWD":/repo -w /repo ghcr.io/gitleaks/gitleaks:v8.30.1 git --config .gitleaks.toml --redact --no-banner
```

Если gitleaks нашёл секрет в коммите, которого ещё нет на remote, пуш запрещён. Секрет убирают из истории до отправки и считают скомпрометированным.

Дальше каждая задача идёт своей веткой. Перед пушем ветки повторяют пункты про индекс и проверки.

## Секреты

- Не коммитить `.env`, ключи, дампы, токены и файлы сертификатов (`.pem`, `.key`, `.crt`, `.cer`, `.csr`, `.p12`, `.pfx`). Файл с примером переменных — только `.env.example` и `infra/.env.example`, без значений.
- Не читать `.env`, `infra/.env`, `infra/.env.prod` и `infra/safeline/.env`, чтобы «посмотреть, как устроено». Имена переменных берут из `infra/.env.example` и `infra/safeline/.env.example`.
- Не выводить секреты в логи, тесты, фикстуры и ответы.
- `service_role` не попадает в `NEXT_PUBLIC_*`, в браузерный бандл и в репозиторий.

## Зависимости

Перед добавлением пакета проверить, что он существует и поддерживается: `npm view <name> version time` для npm, `deno info` для Deno-импорта. Не добавлять пакет с опечаткой, архивный пакет без сопровождения и пакет, который дублирует уже подключённую библиотеку.

## Проверки

Локальный список перед пушем собран в разделе «Перед пушем». CI повторяет его и добавляет проверку портов в compose. Job SonarQube **опционален**: без `SONAR_HOST_URL` и `SONAR_TOKEN` он пропускается, пайплайн остаётся зелёным. Дефолтный прод (`npm run up:prod`) Sonar не поднимает. Образ и профиль `sonar` остаются для отдельного хоста (`docs/production.md`).

Deploy: push в `main` запускает `.github/workflows/deploy.yml` (SSH → `git pull` → compose `up -d --build`), если заданы секреты `DEPLOY_*`. Без них job пропускается (репозиторий шаблона и сервис до первого VPS остаются с зелёным CI). SafeLine деплой не перезапускает. Workflows одни и те же у каркаса и у сервиса из шаблона.

## Ограничения, которые не обходят

- Профиль пользователя нельзя создать триггером на `auth.users`. Таблицу профиля заполняет Edge Function или клиент после входа.
- Плагин ветвей SonarQube неофициальный. Версию сервера и версию плагина меняют только вместе. Сейчас это SonarQube `26.5.0.122743-community` и плагин `26.5.0`.
- Порты в compose-файлах не публикуют на `0.0.0.0`. Локально это `127.0.0.1`. В проде приложение и Kong слушают приватный `UPSTREAM_ADDR`: SafeLine 9.4.3+ не принимает `127.0.0.1` как upstream. Публичный трафик идёт только через SafeLine (`docs/production.md`). Postgres в проде на хост не публикуется. CI-джоба `compose` проверяет это и падает.
- В окружении контейнера функций переменная `SUPABASE_SERVICE_ROLE_KEY` есть, потому что так устроен self-hosted runtime. Код функции её не читает, пока в PR нет отдельного обоснования.
